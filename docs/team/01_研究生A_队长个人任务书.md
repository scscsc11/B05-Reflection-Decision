## 3. 具体任务

### A. 反思机制（核心任务）
维护 `reflection.py`：
- 梳理初判、复核、反馈和停止条件；
- 记录初判与复核结果；
- 记录每轮调用、耗时、是否改变结果；
- 区分有参考反馈的实验与无答案盲测；
- 设计可解释的复核触发和停止记录；
- 与 `llm_client.py` 通过稳定函数接口协作。

### B. 知识演进（核心任务）
维护 `experience_store.py`：
- 管理经验版本、来源和适用条件；
- 保留 verified/unverified/rejected 等状态及其依据；
- 记录冲突经验和处理过程；
- 防止未验证经验被误当作可靠知识；
- 记录哪些经验实际被检索、筛选并发送给模型；
- 保留历史数据库和实验记录，不破坏现有数据。

### C. 实验评分与评价
维护 `score_benchmark.py` 和相应测试：
- 固定案例划分和评价口径；
- 记录初判、复核和最终结果；
- 统计改对、改错、持平、请求次数和耗时；
- 保证答案与推理输入隔离；
- 对小样本结论明确限制，不夸大效果。

### D. 主程序和系统集成
维护 `main.py`、`scene_io.py`：
- 核对官方输入输出契约；
- 创建 `docs/architecture/INTERFACE_CONTRACT.md`；
- 定义 processor 的调用契约和异常边界；
- 接入研究生B交付的 `llm_client.py` 和 `processor.py`；
- 统一输出目录和结果校验；
- 创建 `test_team_integration.py`。

### E. 自主场景统筹
创建 `docs/scenario/SCENARIO_DESIGN.md`，确定材料结构、版本和报告要求。本科生二负责文件整理和一致性核查。

## 4. 与研究生B的协作边界

你提供：
- LLM 客户端供 `reflection.py` 调用的函数契约；
- processor 的 `process(scene, mode)` 输入输出契约；
- 反思模块需要的模型输出结构；
- 统一测试和集成验收要求。

研究生B提供：
- 真实模型客户端；
- processor 核心实现；
- 对应模块说明和模块级测试。

接口变更必须先沟通。你不直接改研究生B文件；研究生B也不直接改你负责的文件。

## 5. 输入与输出

输入：官方资料、当前源码、研究生B模块交付、本科生实验和运行记录。

输出：
- 反思和知识模块；
- 评分与实验评价程序；
- `INTERFACE_CONTRACT.md`；
- `SCENARIO_DESIGN.md`；
- `INTEGRATION_CHECKLIST.md`；
- 集成后的主程序和场景 IO；
- 可运行候选版本和合并记录。
